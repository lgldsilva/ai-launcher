## 1. Blockers in the uncommitted working tree

`git status` shows `cmd/ai-launcher/main.go` modified plus untracked
`internal/launcher/sensitive_paths{,_test}.go` **and** a byte-identical copy of
both files at the repository root.

### B1 — The F1 permission check can never pass (fail-closed, unescapable)

`cmd/ai-launcher/main.go:372-396` builds the permission map with dashed values:

```go
permissionFlagName := map[string]string{
    "ssh": "--ssh", "github": "--gh", "gh": "--gh", "docker": "--docker", ...
    "systemd-user": permissionSystemdUser,   // = "systemd-user", no dashes
}
...
if !flagsWasSet(flags, flagName) {
    return fmt.Errorf("local config enables permission %q (true); pass %s ...", permID, flagName)
}
```

`flagsWasSet` (line 1252) matches `f.Name == name`, and `flag.Flag.Name` is the
**bare** name (`ssh`, not `--ssh`). So `flagsWasSet(flags, "--ssh")` is always
false. Effect: any workspace `.ai-launch.yaml` with a permission set to `true`
is refused *even when the operator passes the exact flag the error tells them to
pass*. There is no way out except `--save` or deleting the key.

`systemd-user` is the only entry that works, and only by accident — its value is
the bare constant. That inconsistency is the tell that this map was
hand-transcribed.

The committed version on `origin/feature/security-trust-gate-hardening`
(`654a578`) has it right: bare names in the map, `"pass --%s"` in the message.

### B2 — Duplicate `package launcher` files at the repository root

`./sensitive_paths.go` and `./sensitive_paths_test.go` are `diff`-identical to
the `internal/launcher/` versions. They declare `package launcher` in the module
root. Delete them — they are dead weight in `go build ./...`, in the Sonar
`sonar.sources=.` scan, and a trap for the next reader.

### B3 — `gofmt` violations will fail the `lint` CI job

The struct literal at `main.go:262-266` and the field block at `309-320` are
misaligned:

```go
trust := localTrust{
    optionsRaw:   !overrides.options,
    fromFile:       flagAgent == "" && !overrides.agent,   // over-padded
    rawPermissions: copyPermissions(raw.Permissions),

```

`.github/workflows/ci.yml` runs `gofmt -l .` and exits non-zero on any output.
The branch already carries `54a0317 style: gofmt main and trust tests` — this
copy predates it.

### B4 — Mangled doc comment on `globalRequiresJail`

`main.go:417-420`:


## 2. Logic defect in the trust boundary (present on the branch too)

### T1 — `rawPermissions` ignores the profile override

`profileBlocks` (`main.go:290-294`) tracks `agent`, `mounts`, `options` — but
not `permissions`. Yet `applyProfile` (line 797) does replace them:

```go
if profile.Permissions != nil {
    local.Permissions = profile.Permissions
}
```

`localTrustFrom` unconditionally copies `raw.Permissions` into
`trust.rawPermissions`, so with `--profile X` where `X` declares its own
permissions block, the file's permissions are discarded from the merged
selection *and still refuse the launch*.

This is exactly the class of bug the comment at `main.go:255-259` says was fixed
for `agent` and `jail`: *"A value a trusted source replaced never reaches the
argv, so refusing the launch over it would block on input that was already
discarded."* The permissions path never got the same treatment.

Fix: add `permissions bool` to `profileBlocks`, set it from
`profile.Permissions != nil`, and gate `rawPermissions` on `!overrides.permissions`
— mirroring what `optionsRaw` does for yolo/extra_args/jail_flags.

### T2 — `extraArgs` guard is inconsistent with its siblings

`jailFlags` and `yolo` are both checked under `if trust.optionsRaw && ...`;
`extraArgs` is checked bare (`if len(trust.extraArgs) > 0`). It happens to be
correct today only because `extraArgs` is populated inside the same
`optionsRaw` branch. Make the three read the same way or the next edit will
break it.

### T3 — `param_values` is not in the trust boundary

`Options.ParamValues` is file-supplied and lands in the argv via
`appendDeclaredParams`. F3 refuses `jail_flags`, F6 refuses `yolo` and
`extra_args`, but nothing refuses a repository-supplied `param_values`. Catalog
params are constrained to declared flags, so the blast radius is smaller than
`extra_args` — but the asymmetry deserves either a check or a recorded decision
in `docs/design-decisions.md`.

## 3. Upstream drift: ai-jail v1.16.0

**ai-jail v1.16.0 shipped 2026-07-25** in response to issue #88 ("Sandbox escape
via a docker socket passthrough (effective host root)"). Up to and including
v1.15.x, ai-jail mounted `/var/run/docker.sock` read-write **automatically**
whenever it existed on the host — no flag, no warning. v1.16.0 flipped it to
opt-in (`--docker` / `no_docker = false`), prints a launch warning when enabled,
and `ai-jail status` now reports `disabled (default)`.

### U1 — The version floor is one release behind the fix (security-relevant)

`internal/config/config.go:62` still pins `MinAIJailVersion = "1.15.0"`.

README claims, under **Security**: *"every permission (ssh, gh, docker, gpu …)
off by default"*. On ai-jail 1.15.x that statement is **false** — the launcher
emits no docker flag at all, so ai-jail auto-mounts the socket and the agent has
host root. The launcher's own documented posture only holds on ≥ 1.16.0.

Bump the floor to `1.16.0`. This is the sharpest finding in the review: the
product promise is "a sandbox that is actually on", and this is the one path
where it silently is not.

### U2 — There is no way to force Docker off

`config.JailFlags` (config.go:204-231) has fields for `lockdown`,
`private_home`, `tailscale`, `gpu`, `display`, `mise`, `worktree`, `landlock`,
`seccomp`, `rlimits`, `status_bar`, `hide_config` — but **no `Docker`**. And
`jailPermissions()` (builder.go:342) declares `{id: "docker", flag: "--docker"}`
with no `override`.

So the launcher can turn Docker on and can never turn it off. `--no-docker` is
unreachable from any configuration surface. Add `Docker *bool` to `JailFlags`,
add it to `jailToggles()` and `IsZero()`, and wire the `override` on the docker
permission — the same tri-state treatment every other capability already has.
Belt and braces on 1.16.x; the actual fix on 1.15.x.

### U3 — `gpu` requiring `docker` forces users into the dangerous flag

`config.go:562`: `{ID: "gpu", Name: "GPU passthrough", Requires: []string{"docker"}}`.

In ai-jail these are independent capabilities (`--gpu` and `--docker`). The
dependency looks launcher-invented, and post-v1.16.0 its effect is to make
"I want GPU passthrough" imply "give the agent host root". Upstream's own
guidance in the v1.16.0 write-up is *"if you wouldn't blindly hand `sudo` to the
agent in that directory, don't hand it `--docker` either."* Either drop the
dependency or document the concrete ai-jail behaviour that justifies it.

### U4 — Contract suite and docs still say v1.15

`AGENTS.md:43`, `docs/design-decisions.md`, README, and the Gherkin scenarios
all describe "ai-jail v1.15 `--no-*` toggles". Per AGENTS.md, when upstream
changes the contract is updated together with the code in the same commit —
that commit has not happened for 1.16.0.

## 4. Upstream: ai-memory

`MinAIMemoryVersion = "1.19.0"` is already ahead of what upstream's July
write-up describes (1.17.1), so no floor bump is needed. Three opportunities:

### M1 — `MemoryRunHarnesses` includes `kimi` and `grok` **[verify]**

The launcher declares eight accepted harnesses: `claude, codex, opencode, pi,
crush, omp, kimi, grok`. Upstream's managed-mode list as documented is *Claude
Code, Codex, OpenCode, Pi, Crush, and OMP*, and the author explicitly separates
"has MCP + a hook" (Kimi Code, Grok Build CLI, Devin, Zero got integrations)
from "has an `ai-memory run` native-session adapter". If `ai-memory run kimi` is
still rejected at 1.19.0, pre-flight passes and the rejection surfaces as an
opaque error inside the jail — the exact failure mode `memory-harness-unsupported`
exists to prevent. Confirm against the installed binary's `--help` and against
the upstream support matrix.

> **2026-08-02:** verified against ai-memory 1.21.0. `ai-memory run --help`
> accepts exactly those eight names. No change needed.

### M2 — `ai-memory workstream-search` is not surfaced

The launcher owns workstream creation (`--new`) and resumption (`--workstream`)
but offers no way to search the ledger. A `ai-launcher --workstream-search
"query"` passthrough, or at minimum a TUI hint, would close the loop on the
feature the launcher already half-drives.

> **2026-08-02:** shipped in v0.3.0 and **broken on delivery** — upstream also
> requires `--workstream-id`, which the launcher never sent, so every search was
> refused by the argument parser. The stub-based tests asserted the launcher's
> own argv and could not see it. Fixed in `fix/workstream-search-id`.

### M3 — `install-instructions` is not part of the install flow

`--install` provisions binaries and (for `pi`) runs `install-hooks`. Upstream
now ships `ai-memory install-instructions`, which installs/updates the managed
Agent Skills that replace the hand-maintained routing block in `CLAUDE.md` /
`AGENTS.md`. Running it after a managed ai-memory install would keep the
protocol from drifting per-repo.
